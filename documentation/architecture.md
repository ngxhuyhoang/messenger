# Architecture overview

This repo has four independent projects. Each one has its own build tool and its own code. The three mobile apps are meant to talk to the same backend, but none of them can do that successfully yet (see [Known gaps](#known-gaps)).

```
messenger/
├── flutter-messenger/   Flutter app (Dart)          working on login
├── android-messenger/   Native Android (Kotlin)     app skeleton
├── ios-messenger/       Native iOS (Swift)          "Hello, world!" stub
└── backend/             NestJS server (TypeScript)  sample route only
```

## Pattern: MVVM on all three platforms

All three mobile apps use **MVVM** (Model - View - ViewModel). The UI toolkits are:

- **Flutter:** widgets.
- **Android:** Jetpack Compose.
- **iOS:** SwiftUI.

| Part | Job | Flutter | Android | iOS |
| --- | --- | --- | --- | --- |
| **View** | Draws the state and sends user actions to the ViewModel. It has no business logic. | `Login`, `Home`, `Splash` | `MainScreen` (`@Composable`) | `ContentView` |
| **ViewModel** | Holds the state of one screen and the logic for it. It knows nothing about the View. | `LoginCubit` today (see the note below) | `MainScreenViewModel` | Not built yet (plan: an `@Observable` class) |
| **Model** | Data and data access: repositories, services, DTOs. | `AuthRepository`, `AuthService`, DTOs | `DataRepository` | Not built yet |

Rules for every platform:

1. The View never calls a repository or a service directly. It only talks to its ViewModel.
2. The ViewModel never imports UI types (no `BuildContext` in Flutter, no `Context` in Android, no `View` in SwiftUI).
3. The ViewModel exposes the screen state, and the View only reads it.
4. The repository hides how the data is loaded. The ViewModel does not know about Dio, HTTP or JSON.

Open decision for Flutter: the repo has both `LoginCubit` and an empty `LoginViewModel` (`features/auth/view_models/login_view_model.dart`). `LoginCubit` does the ViewModel's job today. The plan is to keep only one of them. See [Known gaps](#known-gaps).

## Flutter (`flutter-messenger/lib/`)

### Startup

1. `main.dart` calls `runApp(const App())`.
2. `app.dart` builds `App`. It uses `MultiRepositoryProvider` to provide one `AuthRepository` (created with an `AuthService`) to the whole app.
3. `MaterialApp.router` uses the `router` from `shared/common/router.dart`.

### Routes

| Path      | Screen   | Notes                                                         |
| --------- | -------- | ------------------------------------------------------------- |
| `/login`  | `Login`  | Initial route. It is wrapped in a `BlocProvider<LoginCubit>`. |
| `/home`   | `Home`   | Placeholder (shows the text "Home").                          |
| `/splash` | `Splash` | Placeholder. It exists, but it is not the initial route.      |

### Layers of the login flow

```
Login (view)
  → LoginCubit            features/auth/cubits/
    → AuthRepository      features/auth/repositories/
      → AuthService       features/auth/services/
        → connectionInstance (Dio)   services/connection_instance.dart
```

- **View** (`features/auth/views/login.dart`): shows the form, validates the email and the password, and calls `LoginCubit.login(email, password)`. A `BlocListener` reacts to the state. On `LoginSuccess` it calls `context.go('/home')`. The input validation lives in the View today. In MVVM it would usually move to the ViewModel, so you can test it without a widget.
- **Cubit** (`login_cubit.dart`): holds the screen state. It plays the **ViewModel** role today. It ignores a second call while the state is `LoginLoading`, and it checks `isClosed` before it emits a new state.
- **Repository** (`auth_repository.dart`): builds the `LoginRequestDto` and calls the service.
- **Service** (`auth_service.dart`): sends the HTTP request with the shared Dio instance.

### State

`LoginState` is a sealed class, so the compiler can check that every case is handled:

| State                   | Meaning                                               |
| ----------------------- | ----------------------------------------------------- |
| `LoginInitial`          | Nothing happened yet.                                 |
| `LoginLoading`          | A login request is running.                           |
| `LoginSuccess`          | Login worked.                                         |
| `LoginFailure(message)` | Login failed. `message` comes from an `AppException`. |

### Models and shared code

- `LoginRequestDto`: `email`, `password`. It only has `toJson`.
- `LoginResponseDto`: `accessToken`, `refreshToken`. It only has `fromJson`.
- `BaseResponse<T>`: `isSuccess`, `message`, `data`. This is the wrapper the app expects from the API.
- The `*.g.dart` files are generated by `json_serializable`. Run `build_runner` to create them (see the [setup guide](setup-guide.md)).
- `shared/common/`: `AppException`, `AppColor` (primary color), `AppConfig` and `AppEnvironment` (development or production), and the router.
- `services/connection_instance.dart`: the Dio instance (base URL, 10 second connect timeout) and `setAuthHeader()`, which adds or removes the `Authorization: Bearer ...` header.

### Tests

`test/widget_test.dart` has widget tests for the login form: empty fields, a wrong email, a short password, a valid form, and the show/hide password button.

## Android (`android-messenger/app/src/main/java/com/example/messenger/`)

### Startup

```
MainActivity
  → MessengerTheme
    → Surface
      → MainNavigation          Navigation.kt
        → MainScreen            ui/main/MainScreen.kt
```

- **Navigation 3**: `MainNavigation` creates a back stack with `rememberNavBackStack(Main)` and shows it with `NavDisplay`. `entryProvider` maps each key to a screen. The keys are `@Serializable` objects in `NavigationKeys.kt`. Today there is only one key, `Main`.
- **ViewModel** (MVVM): `MainScreen` creates `MainScreenViewModel(DefaultDataRepository())`. The screen only reads the state from it.
- **UI state**: the ViewModel exposes a `StateFlow<MainScreenUiState>`. The state is `Loading`, `Success(data)` or `Error(throwable)`. It is built with `stateIn(viewModelScope, SharingStarted.WhileSubscribed(5000), Loading)`, so the flow stops 5 seconds after the last collector goes away.
- **Data**: `DataRepository` is an interface with a `Flow<List<String>>`. `DefaultDataRepository` emits `["Android"]`.
- **Theme**: `theme/` has `Color.kt`, `Theme.kt` and `Type.kt`.
- **Tests**: `MainScreenViewModelTest` (unit test) and `MainScreenTest` (UI test).

## iOS (`ios-messenger/`)

A SwiftUI project. `MyApp.swift` is the entry point and `ContentView.swift` shows "Hello, world!". Nothing else is built yet, so there is no ViewModel. When you build the login screen, the plan is a `LoginViewModel` class marked `@Observable`, owned by the View.

## Backend (`backend/src/`)

```
AppModule
  → AppController   GET /
    → AppService    returns the hello text
```

The server listens on the port from the `PORT` environment variable, or `3000` if it is not set. There is no database, no authentication, and no `/api` prefix yet.

## Known gaps

These are facts about the current code, not bugs I fixed. They are good exercises.

| #   | Gap                                                                                                      | Where                                             |
| --- | -------------------------------------------------------------------------------------------------------- | ------------------------------------------------- |
| 1   | Flutter calls `http://localhost:4299/api`, but the backend listens on port `3000` with no `/api` prefix. | `connection_instance.dart`, `backend/src/main.ts` |
| 2   | Flutter calls `POST /auth/login`, but the backend only has `GET /`.                                      | `auth_service.dart`, `app.controller.ts`          |
| 3   | `AuthRepository.login` does not read the response or save the tokens.                                    | `auth_repository.dart`                            |
| 4   | The `LoginFailure` branch in the view only has a "Do something here" comment, so the user sees no error. | `login.dart`                                      |
| 5   | `AuthService.logout()` sends a `POST` to `/auth/login`.                                                  | `auth_service.dart`                               |
| 6   | `AuthService.login()` returns `Future<Future<Response>>`. One `Future` is enough.                        | `auth_service.dart`                               |
| 7   | `LoginViewModel` is an empty class, and the `AuthStatus` enum is not used.                               | `login_view_model.dart`, `app_enum.dart`          |
| 8   | Flutter has two candidates for the ViewModel role: `LoginCubit` and the empty `LoginViewModel`. Keep one. | `login_cubit.dart`, `login_view_model.dart`       |
| 9   | iOS has no ViewModel yet, and Android has no login screen yet.                                           | `ios-messenger/`, `android-messenger/`            |
